# 0. 이번 개정의 결론

## 0-1. 현재 실제 완료 기준

현재 앱은 네트워크 없이 동작하는 1~7단계 로컬 제품 마일스톤까지 구현되어 있다.

- iPad 전용 SwiftUI 앱과 UIKit/TextKit 기반 편집기
- UTF-8 TXT 단일 원본과 SwiftData 메타데이터 분리
- 작품 생성·이름 변경·삭제 목록·Windows 작품 가져오기
- 고정 바인더, 일반 폴더·TXT, 원고 권·화 규칙과 새 권 25화 생성
- 한글 IME 보호, 스마트 입력, 글자 수, 화면 설정, 물리 키보드 명령
- 좌우 듀얼 편집기와 작품별 화면 상태 복원
- 800ms 자동 저장, 즉시 저장, 원자 저장, 저장 실패 전환 차단
- 로컬 백업·미리보기·diff·복원·휴지통·영구 삭제
- 현재 문서 검색·작품 전체 검색
- 개인 소장용 UTF-8 TXT·PDF 원고 내보내기
- 1,000화·보조 TXT 500개·백업 5,000개 성능 기준선

현재 서버 기능은 구현되어 있지 않다.

- `supabase-swift` 패키지 없음
- URLSession 기반 서버 클라이언트 없음
- 인증·Keychain 세션 없음
- 설치별 `device_id` 없음
- 서버 revision·operation queue·lease·Realtime·pull 없음
- Swift 3방향 병합과 충돌 해결 화면 없음
- `FutureChangeNotifying`와 `NoOpFutureChangeNotifier`만 존재

따라서 새 8단계는 “기존 서버 구현을 이어 붙이는 단계”가 아니라 “완성된 로컬 제품을 손상시키지 않고 서버 경계를 처음 도입하는 단계”로 시작한다.

## 0-2. 기존 계획에서 유지하는 것

- Windows/Supabase v2의 UUID, revision, operation_id, lease, tombstone 계약
- 로컬 저장 완료와 서버 동기화 완료의 분리
- SQLite 영구 큐와 같은 operation_id 재시도
- Realtime payload를 원문으로 신뢰하지 않고 snapshot pull의 신호로만 사용
- Base·Local·Remote 3방향 병합
- 숨은 `tree-order.json`, `trash-purge.json`
- Windows A/B와 실제 iPad의 교차 수용 테스트
- TestFlight 전 실제 기기 lifecycle·성능·개인정보 감사

## 0-3. 기존 계획에서 변경하는 것

1. 서버 상태를 기존 SwiftData `DocumentRecord`에 바로 추가하지 않는다.
   - 현재 `WriterPadSchemaV1`은 로컬 메타데이터와 화면 복원을 안정적으로 담당한다.
   - 서버 revision, base_content, operation, conflict, binding은 별도 `SyncV2Store` SQLite에 둔다.
   - SwiftData V2는 실제로 로컬 화면 projection이 필요하다는 근거가 생긴 경우에만 추가한다.

2. 현재의 `FutureChangeNotifying`를 그대로 큐로 바꾸지 않는다.
   - 현재 사건에는 rename, move, reorder, project rename, path, 본문 snapshot이 부족하다.
   - 현재 `record`는 오류를 반환하지 않아 영구 큐 등록 실패를 숨길 수 있다.
   - 8단계에서 사건표와 저장 책임을 먼저 확정한 뒤 durable recorder로 교체한다.

3. 로컬 백업과 서버 버전 기록을 합치지 않는다.
   - `LocalBackupStore`는 사용자 복원용 로컬 안전망이다.
   - 서버 `document_versions`와 동기화 conflict 자료는 별도 책임이다.

4. 원고 내보내기는 동기화·백업·가져오기 수단으로 확장하지 않는다.
   - ADR-010에 따라 TXT·PDF 개인 소장용 기능으로 유지한다.

5. 현재 코드에 없는 서버 정책을 기획서가 임의로 확정하지 않는다.
   - 빈 폴더, 폴더 자체 UUID, 작품 영구 삭제, 계정 가입, 공유 권한 편집은 계약 감사에서 결정하거나 보류한다.
   - 새 RPC나 테이블이 필요하면 재현 테스트와 호환성 보고 후 순방향 migration 승인을 받는다.

6. 참조 파일 경로를 현재 저장소에 맞춘다.
   - SQL: `참조파일/20260714000000_supabase_v2_protocol.sql`
   - SQL 보정: `참조파일/20260714010000_windows_v2_client_support.sql`
   - Windows v2: `참조파일/sync_manager.py`, `sync_v2_store.py`, `three_way_merge.py` 등

## 0-4. 기존 계획에 새로 추가하는 위험

- 현재 Git 작업 트리에 1~7단계 변경이 많이 남아 있으므로 8단계 시작 전 복구 가능한 기준 commit을 확정해야 한다.
- Swift 편집 버퍼에도 `revision`이라는 이름이 있으므로 서버 revision과 혼동하지 않게 `serverRevision` 등으로 명명한다.
- 서버 `commit_document`는 본문 UTF-8 크기를 10MiB로 제한한다. 큰 로컬 TXT는 저장 성공을 유지하되 서버 전송 불가 상태를 별도로 보여야 한다.
- 서버 경로 검사는 로컬 Windows 안전 이름 정책보다 느슨할 수 있다. iPad는 현재의 더 엄격한 `PathPolicy`를 유지한다.
- 현재 로컬 바인더는 폴더 노드도 UUID를 가진다. 서버 v2 문서 모델이 빈 폴더를 직접 표현하지 않는다면 빈 폴더 교차 기기 보존 정책이 필요하다.
- 현재 작품 삭제 목록과 서버 프로젝트 삭제는 서로 다른 개념이다. 서버 삭제 계약이 없으므로 자동 전파하지 않는다.
- 현재 듀얼 편집기는 같은 문서를 양쪽에서 열 수 있다. lease는 편집기 칸별이 아니라 `document_id`별 하나여야 한다.

# 1. 8단계 진입 전 공통 원칙

## 1-1. 데이터 원본과 저장 성공

- 사용자 원고의 로컬 원본은 계속 UTF-8 TXT다.
- SwiftData는 로컬 문서 정체성·경로·화면 상태를 담당한다.
- SyncV2 SQLite는 서버 기준본·revision·operation·binding·conflict를 담당한다.
- LocalBackupStore는 로컬 복구본을 담당한다.
- 로컬 TXT 저장 성공은 네트워크·인증·서버 성공 여부와 독립이다.
- 서버 큐 등록 실패는 로컬 저장 실패로 되돌리지 않지만, 원격 반영이 보장되지 않는 고위험 상태로 표시한다.

## 1-2. 테스트와 서버 안전

- 운영 작품과 운영 원고를 테스트에 사용하지 않는다.
- 서버 테스트는 전용 계정과 매번 새 UUID 프로젝트를 사용한다.
- 이미 적용되었다고 전달된 두 SQL 파일은 다시 실행하지 않는다.
- 실제 적용 여부는 Supabase migration history 또는 읽기 전용 schema 확인으로 검증한다.
- 계약 결함이 있어도 앱 코드에서 추측성 우회 테이블을 만들지 않는다.
- 시뮬레이터 결과를 실제 iPad 결과로 기록하지 않는다.

## 1-3. 단계별 중단 규칙

각 `지금부터` 블록이 끝나면 다음을 보고하고 중단한다.

- 변경 파일
- 자동 테스트 결과와 실행하지 못한 테스트
- 실제 iPad 검증 여부
- Windows 참조 구현과의 차이
- 로컬 TXT·SwiftData·SyncV2 SQLite에 미치는 영향
- 다음 세부 단계 진입 조건

- 상대 경로 최대 길이와 금지 형태를 확인한다.
- 서버 hash, revision, committed_at 응답 필드를 fixture로 고정한다.
- 숨은 문서는 일반 문서와 같은 commit 계약을 쓰되 UI에서 제외한다.

- 새 서버 migration 필요 여부를 결론내린다.

## 8-3. 로컬 사건과 서버 사건 매핑

### 지금부터

현재 코드의 실제 변경 사건을 전부 표로 만든다.

- 앱 시작
- 작품 생성·이름 변경·삭제 목록 이동·복원·영구 삭제
- TXT 생성·저장·이름 변경·이동
- 폴더 생성·이름 변경·이동·삭제
- 새 권과 25화 일괄 생성
- 문서 휴지통 이동·복원·영구 삭제·전체 비우기
- 바인더 순서 변경
- 백업 복원
- Windows 작품 가져오기
- 원고 내보내기

각 사건을 다음 중 하나로 분류한다.

- v2 문서 commit
- 숨은 tree-order commit
- 숨은 trash-purge commit
- 프로젝트 `ensure_project`
- 로컬 전용
- 서버 계약이 없어 보류

현재 `LocalChangeEvent`에서 빠진 path·본문 snapshot·generation·rename·move·reorder를 확인한다. durable queue 등록 실패를 호출자가 알 수 있도록 새 protocol은 오류 또는 명시적 결과를 반환해야 한다.

특히 다음 정책을 확정한다.

- 백업 복원은 복원된 본문을 새 로컬 수정으로 enqueue한다.
- Windows 가져오기 문서는 사용자 확인 후 한 번에 서버 연결한다.
- 원고 내보내기는 로컬 전용이다.
- 로컬 백업 파일은 서버에 올리지 않는다.
- 작품 삭제는 서버 삭제 RPC가 없으므로 기본적으로 로컬 전용이다.
- 빈 폴더 보존은 tree-order 숨은 문서로 가능한지 검증하고, 불가능하면 기능 제한을 명시한다.
- 듀얼 편집기의 같은 문서는 하나의 저장 generation·하나의 문서 큐 순서를 사용한다.

### 완료 조건

- 현재 모든 로컬 변경 사건이 누락 없이 분류된다.
- `FutureChangeNotifying` 유지·교체·호환 adapter 계획이 확정된다.
- 폴더와 작품 삭제의 교차 기기 정책이 문서화된다.

- resolved_at

설계 원칙:

- SQLite WAL과 foreign key를 켠다.
- 모든 접근은 `SyncV2Store` actor 하나로 직렬화한다.
- 전체 본문 중복은 `base_content`, pending payload, conflict 원본이라는 동기화 책임에만 허용한다.
- SwiftData V1이 열리지 않아도 TXT를 손상시키지 않는다.
- SyncV2Store가 열리지 않아도 로컬 앱은 실행되고 저장된다.
- SyncV2Store 생성·migration 실패는 서버 기능만 비활성화하고 진단한다.
- 1~7단계 사용자는 별도 DB를 처음 생성하므로 SwiftData migration은 하지 않는다.
- 향후 SyncV2Store schema version과 순방향 migration을 처음부터 둔다.

### 완료 조건

- SQLite schema와 transaction 경계가 문서화된다.
- SwiftData V1 무변경 결정 또는 변경 필요성이 근거와 함께 확정된다.
- migration 실패·저장 공간 부족·DB 손상 복구 정책이 있다.

### 여기까지

## 8단계 완료 조건

- 1~7단계 기준선이 복구 가능하게 고정됐다.
- 실제 SQL·Windows v2 계약 문서가 있다.
- 모든 로컬 사건의 서버 매핑이 확정됐다.
- SyncV2Store가 SwiftData·로컬 백업과 분리 설계됐다.
- 빈 폴더·작품 삭제·큰 파일 정책의 미결정 사항이 숨겨지지 않았다.

# 4. 10단계 — 영구 operation queue와 로컬 저장 연결

## 10-1. SyncV2Store 구현

### 지금부터

8-4의 schema를 구현하고 fixture DB로 검증한다.

- 새 DB 생성
- WAL 재오픈

- 1,000건 queue

### 여기까지

## 10-2. enqueue와 문서별 순서

### 지금부터

operation 상태는 최소 다음을 구분한다.

- pending
- inflight
- completed
- conflict
- cancelled

같은 문서의 작업은 순서를 보존한다. 아직 전송하지 않은 동일 본문 저장은 안전할 때만 합친다. rename, move, delete, restore는 서버 기준을 모른 채 제거하지 않는다.

operation_id는 생성 후 재시도·재실행·네트워크 전환에도 바꾸지 않는다.

### 여기까지

## 10-3. LocalDocumentStore·저장 세션 연결

### 지금부터

현재 저장 순서를 유지한다.

1. 편집기 snapshot 확정
2. 로컬 TXT 원자 저장
3. 로컬 SHA-256·SwiftData 갱신
4. durable operation enqueue
5. UI 상태 갱신

IME 조합 중간 본문을 enqueue하지 않는다. 저장 generation이 역전되면 오래된 operation이 최신 본문으로 가장하지 않게 한다. 같은 문서를 좌우에서 열어도 document queue는 하나다.

enqueue 실패는:

- 로컬 저장 성공을 취소하지 않는다.
- `로컬 저장됨 · 동기화 기록 실패`처럼 고위험 상태로 표시한다.
- 사용자가 다시 기록할 수 있게 한다.
- 다음 저장에서 조용히 사라지지 않는다.

### 여기까지

## 10-4. 구조 변경·복원·가져오기 연결

### 지금부터

다음을 durable 사건으로 연결한다.

- TXT 생성
- 이름 변경·이동
- 휴지통 이동
- 휴지통 복원
- 백업 복원 후 본문 변경
- 새 권 25화
- Windows 가져오기 후 명시적 서버 연결
- 바인더 reorder
- 휴지통 영구 삭제·비우기

로컬 거래가 완료되기 전 operation을 만들지 않는다. 대량 작업 중 일부 operation만 기록되는 문제를 막기 위해 로컬 거래 결과와 queue 등록 결과의 복구 저널을 설계한다.

### 여기까지

## 10-5. 10MiB preflight와 no-op 저장

### 지금부터

UTF-8 byte count가 서버 제한을 넘는 문서는 로컬 저장과 백업을 계속 허용한다. 서버 요청 전에 차단하고 `서버 크기 제한 초과` 상태로 보존한다.

서버 revision·server_path·base_content와 같고 활성 operation이 없는 동일 본문 저장은 새 revision을 만들지 않는다.

### 여기까지

## 10단계 완료 조건

- 로컬 저장 후 operation이 영구 보존된다.
- 강제 종료 후 같은 operation_id로 복구된다.
- queue 실패와 서버 크기 제한이 로컬 저장 실패로 표현되지 않는다.
- 저장·rename·move·delete·restore·reorder 사건이 누락되지 않는다.

# 5. 11단계 — commit·재시도·lease·원격 pull

## 11-1. commit_document와 오류 분류

### 지금부터

성공 응답에는 revision, content hash, committed_at 등 계약상 필수값이 있어야 한다. 응답 누락은 성공으로 처리하지 않는다.

- revision conflict
- path conflict

서버 성공과 SyncV2Store 반영 사이에 앱이 종료되어도 같은 operation_id 재전송으로 수렴해야 한다.

### 여기까지

## 11-2. dispatcher와 재시도

### 지금부터

문서별 순서를 지키는 제한 동시성 dispatcher를 구현한다.

- 앱 foreground
- 사용자의 명시적 재시도
- 실제 네트워크 복구

위 사건은 즉시 재시도 기회를 준다. `NWPathMonitor`는 기회 신호일 뿐 성공 판정이 아니다. conflict 한 건이 다른 문서 pending을 막지 않는다.

### 여기까지

## 11-3. document_id 단위 edit lease

### 지금부터

`EditLeaseManager` actor를 구현한다.

- revision 0 새 문서는 lease 없이 첫 commit
- 기존 문서는 편집 진입 또는 commit 전 lease 획득
- 활성 document_id별 heartbeat
- 좌우에 같은 문서가 열려도 lease 하나
- 한쪽을 닫아도 다른 쪽이 활성이라면 유지

## 11-4. 서버 snapshot pull

### 지금부터

- 동기화 대기
- 인증 필요

# 6. 12단계 — 3방향 병합과 충돌 해결

## 12-2. 자동 rebase

### 지금부터

revision conflict 시 document_id로 최신 remote를 읽는다.

- Base: operation의 base_content
- Local: 디스크가 아니라 현재 세션 generation까지 고려한 최신 로컬 본문
- Remote: 서버 최신 본문

비겹침이면 remote revision과 remote content를 새 base로 operation을 rebase한다. merge 중 사용자가 더 입력했다면 generation 비교로 오래된 결과 적용을 막는다.

path와 content는 독립적으로 병합하되 다른 UUID가 목적 path를 점유하면 중단한다.

### 여기까지

## 12-3. 충돌 원본 영구 보존

### 지금부터

겹침 충돌에서는 현재 로컬 TXT를 덮어쓰지 않는다.

SyncV2Store에 Base·Local·Remote·Merged·remote revision·remote path·operation_id를 transaction으로 보존한다. 필요하면 기존 `LocalBackupStore`의 충돌 사유를 이용해 사용자용 TXT 사본을 추가하되, sync conflict DB와 로컬 백업의 책임을 합치지 않는다.

재실행 후에도 세 원본을 열 수 있어야 한다.

### 여기까지

## 12-4. iPad 충돌 해결 화면

### 지금부터

Base·내 로컬본·서버 최신본·병합 결과를 비교한다.

- 가로: 비교 패널
- 세로: 탭 또는 단계형 UI
- 세 원본 읽기 전용
- 해결 결과만 편집 가능
- VoiceOver·외장 키보드·회전 지원

해결 저장은 remote revision과 remote content를 새 base로 새 operation을 만든다. 이전 conflict operation은 resolved/cancelled 이력을 남긴다.

### 여기까지

## 12단계 완료 조건

- 겹침은 로컬 TXT를 덮어쓰지 않는다.
- 재실행 후에도 세 원본과 해결 상태가 보존된다.

# 7. 13단계 — tombstone·숨은 문서·경로 복구

## 13-1. 삭제·복원·재삭제

### 지금부터

로컬 휴지통 이동 후 같은 document_id로 `p_is_deleted = true` commit을 등록한다. 생성 직후 삭제도 create 뒤 delete 순서를 유지한다.

복원은 같은 UUID와 더 높은 revision으로 `is_deleted = false`를 commit한다. 원래 path 충돌 시 사용자가 안전한 위치를 선택한다.

늦게 도착한 편집 저장이 삭제된 path를 새 문서로 부활시키지 않게 generation·tombstone 상태를 확인한다.

### 여기까지

## 13-2. tree-order 숨은 문서

### 지금부터

`__antigravity__/tree-order.json`을 프로젝트 설정 문서로 동기화한다.

- 프로젝트 namespace 기반 결정적 UUID
- 일반 바인더·검색·내보내기·휴지통에서 숨김
- 빠른 reorder coalesce
- remote revision 위 rebase
- 폴더 UUID·빈 폴더 표현 가능 여부 검증

빈 폴더를 표현할 수 없다면 조용히 유실시키지 말고 “다른 기기에는 내용이 생길 때까지 나타나지 않음” 등 확정 정책을 UI와 문서에 명시한다.

### 여기까지

## 13-3. trash-purge 숨은 문서

### 지금부터

`__antigravity__/trash-purge.json`에 문서별 purged revision과 전체 비우기 generation을 기록한다.

stale tombstone이 다른 기기에서 다시 나타나지 않게 한다. 같은 UUID가 purge revision보다 높은 revision으로 다시 삭제되면 새 사건으로 허용한다.

### 여기까지

## 13-4. 누락 사본과 경로 충돌 복구

### 지금부터

clean live TXT 또는 tombstone 사본이 사라졌을 때 같은 revision의 remote snapshot으로만 복구한다. pending·inflight·conflict 문서는 자동 복구하지 않는다.

다른 UUID가 점유한 live path는 덮어쓰지 않는다. 휴지통 사본은 document_id가 포함된 안전한 경로로 재배치할 수 있다.

### 여기까지

## 13단계 완료 조건

- 삭제·복원·재삭제가 같은 UUID와 증가 revision으로 동작한다.
- 숨은 문서가 일반 UI와 내보내기에 나타나지 않는다.
- purge 이후 stale tombstone이 부활하지 않는다.
- 빈 폴더 정책이 실제 교차 기기 동작과 일치한다.
- 누락 clean 사본이 원고 손실 없이 복구된다.

# 9. 최종 우선순위와 중단 지점

구현 순서는 반드시 다음을 따른다.

1. 8단계 계약·사건표·저장 경계
2. 9단계 설정·인증·device_id·binding
3. 10단계 durable queue와 모든 로컬 사건 연결
4. 11단계 commit·retry·lease·pull·Realtime·상태 UI
5. 12단계 병합·충돌
6. 13단계 tombstone·숨은 문서·복구
7. 14단계 교차 수용·성능·TestFlight

인증 UI가 보인다는 이유로 queue 없이 문서 commit부터 연결하지 않는다.
Realtime이 연결된다는 이유로 snapshot pull 없이 원격 본문을 적용하지 않는다.
서버 성공을 기다리느라 로컬 TXT 저장을 늦추지 않는다.
SwiftData migration이 필요하다는 근거 없이 V1 모델에 서버 필드를 추가하지 않는다.

14단계 자동 테스트, 실제 iPad 검증, Windows A/B/iPad 교차 테스트, Archive·TestFlight 준비가 끝나면 개발을 중단하고 완료·미검증·알려진 위험을 보고한다.
