###
WriterPad/Sync/SyncV2SnapshotPull.swift 의 SyncV2WorkspaceSyncModel.bindingChanged
에서 취소한 Task ivar 를 nil 로 되돌리지 않는 버그를 고쳐줘.

[확정된 결함]
bindingChanged 의 두 분기 모두 reconnectTask?.cancel() / pullRetryTask?.cancel()
만 하고 nil 대입을 빠뜨렸다. updateSceneActivity(false) 와 stop() 은 둘 다
nil 을 대입하는데 bindingChanged 만 누락이다.

두 스케줄러는 sentinel 기반 단일 실행이다:
  scheduleRealtimeReconnect()  : guard reconnectTask == nil
  schedulePullRetry()          : guard pullRetryTask == nil

취소된 task 본문은 catch { return } 로 빠져나가며 ivar 를 비우지 않는다
(self.reconnectTask = nil 은 sleep 성공 이후에만 실행된다).
따라서 binding 변경 이후 재연결과 pull 재시도가 프로세스 수명 동안 영구
봉쇄된다. 재로그인 시 rebinding 이 일어나므로 "재로그인하면 잠깐 정상,
이후 재발" 증상과 일치한다.

[해야 할 것]
1. bindingChanged 의 serverProjectID == nil 분기에서 cancel 한 모든 task
   (debounceTask, periodicTask, realtimeStartTask, reconnectTask,
   pullRetryTask)에 nil 을 대입한다.
2. bindingChanged 의 serverProjectID 변경 분기에서도 동일하게
   realtimeStartTask, reconnectTask, pullRetryTask 에 nil 을 대입한다.
3. schedulePullRetry() 와 scheduleRealtimeReconnect() 의 Task 본문을 재구성해
   모든 종료 경로에서 sentinel 이 해제되게 한다. 예:

       xTask = Task { [weak self] in
           let didSleep: Bool
           do {
               try await sleep(delay)
               try Task.checkCancellation()
               didSleep = true
           } catch {
               didSleep = false
           }
           guard let self else { return }
           self.xTask = nil
           guard didSleep, self.isActive else { return }
           await self.<다음 동작>()
       }

4. scheduleRealtimeReconnect() 안의
   authenticationService.refreshSession(force: false) 호출을
   취소 확인(Task.checkCancellation) 뒤로 옮긴다.
   지금은 이미 취소된 재연결도 refresh 를 한 번 수행한다.

[하지 말 것]
- pullTask 에는 nil 을 대입하지 마라. finishPull 의 pullRequestID 대조가
  성립해야 in-flight 결과가 새 pull 을 덮어쓰지 않는다.
  15초 watchdog 이 스스로 정리한다.
- 전체 재작성 금지. 최소 수정만.

[완료 기준]
- 빌드 통과, 기존 테스트 전부 통과
- 1번에서 넣은 로그로 "blocked by stale sentinel" 이 더는 반복되지 않을 것

목적: 아직 고치는 게 아니라 "무엇이 실제로 일어나는지" 확인하는 단계입니다.
      이 세션 결과가 3~6번의 우선순위를 다시 정해줍니다.

준비물
  - 아이패드 실기기 (시뮬레이터로는 재현 불가)
  - Mac 에 USB 연결 또는 동일 네트워크
  - Console.app 실행, 기기 선택, 검색창에 subsystem:com.chocos.writerpad 입력

절차

  2. 앱을 포그라운드에 둔 채 1시간 이상 유휴 방치

  3. 스피너가 뜨면 "라벨을 먼저" 확인한다. 이게 원인 분기점이다.

       "서버 동기화 중"                  -> C4 경로  (4번 단계가 대상)
       "서버 재연결 중" / "서버 연결 확인 중" -> C1+C3 경로 (2·3번 단계가 대상)
       "로그인 확인 중"                   -> C7 경로  (6번 단계가 대상)

  4. 로그에서 아래 4가지를 확인하고 기록한다.

       (1) "pullNow start reqID=N" 과 "finishPull reqID=N" 짝이 맞는가?
           start 만 있고 finish 가 없으면 -> C4 확정 (4번 단계 필요)
           짝이 맞으면                    -> C4 배제 (4번 단계 후순위 가능)

       (2) reconnectAttempt 값이 0->1->0 으로 왕복하는가?
           왕복하면 -> C2 확정 (3번 단계 필요)

       (3) gate acquire 와 release 개수가 균형인가? waiters.count 가
           단조 증가하는가?
           증가하면 -> C6 확정 (5번 단계 필요)

       (4) "blocked by stale sentinel" 이 반복되는가?
           반복되면 -> C1 확정 (2번 수정이 효과 있음을 역으로 확인)

       (5) "operation superseded" 가 찍히는가?
           찍히면 -> C7 확정 (6번 단계 필요)

  5. 로그아웃 -> 재로그인 -> 잠깐 정상 -> 다시 유휴 -> 재발하는지 확인
     2번 수정 후에도 재발하면 원인이 C1 만은 아니라는 뜻이다.

기록할 것
  - 스피너 라벨 (정확한 문구 그대로)
  - 정지까지 걸린 시간
  - 위 (1)~(5) 각각의 관찰 결과
  - Console 로그를 파일로 저장 (Console.app 에서 선택 후 저장)

★ 이 세션을 건너뛰고 1~6번을 한꺼번에 적용하면, 무엇이 실제로 효과가
  있었는지 영영 알 수 없게 됩니다. 반드시 하세요.

###
WriterPad/Sync/SyncV2SnapshotPull.swift 의 재연결 hot loop 와
"pull 성공이 화면에 안 보이는" 문제를 고쳐줘. 두 결함은 같은 증상으로 합쳐진다.

[확정된 결함 A — backoff hot loop]
LiveSyncV2RealtimeTrigger.startChannel 은 subscribeWithError() 가 정상 반환하면
항상 .subscribed 를 합성해 올려보낸다.
SyncV2WorkspaceSyncModel.receivedRealtimeStatus 의 .subscribed 분기는 그걸 받아
reconnectAttempt = 0 으로 리셋하고 pullNow(forceVisibleProgress: true) 를 건다.

따라서 "join 은 성공하지만 곧 끊기는" 채널(유휴 후 서버/NAT 가 socket 을 끊은
상태)에서:
    subscribe 성공 -> reconnectAttempt = 0 -> pullNow -> serverState = .syncing
    -> 곧 .channelError -> .reconnecting -> 1초 후 재시도 -> 반복
backoff 가 1초에 고정되고, .syncing 과 .reconnecting 둘 다 progress 상태라
에러가 절대 표시되지 않는다.

[확정된 결함 B — 성공이 표시되지 않음]
complete(_ report:) 마지막 분기가
    } else if realtime != nil && !realtimeHealthy {
        serverState = realtimeProgressState
    } else {
        serverState = .synced(at: Date())
    }
이라서, realtimeHealthy 가 false 로 굳으면 snapshot pull 이 매번 성공해도
화면은 영원히 "서버 연결 확인 중" / "서버 재연결 중" 이다.

[해야 할 것]
1. 결함 A: reconnectAttempt 리셋 조건을 "구독이 실제로 유지된 경우"로 바꾼다.
   - lastSubscribedAt: ContinuousClock.Instant? 프로퍼티를 추가
   - .subscribed 분기: reconnectAttempt = 0 을 제거하고 lastSubscribedAt 만 기록
   - .closed / .channelError / .timedOut 분기: 직전 구독이 30초 이상 유지됐을
     때만 reconnectAttempt = 0 으로 리셋하고, lastSubscribedAt 은 nil 로 되돌린다
2. 결함 B: complete(_ report:) 에서
   `else if realtime != nil && !realtimeHealthy` 분기를 제거해 성공한 pull 이
   항상 .synced(at:) 를 표시하게 한다. realtime 연결 상태 표시는
   receivedRealtimeStatus 가 계속 담당한다
   (.synced 는 preservesHigherPriorityServerState 에 없으므로 다음 콜백이 덮는다).

[트레이드오프 — 그대로 수용할 것]
결함 B 수정 후 재연결 중에도 "서버 동기화됨" 이 잠깐 보일 수 있다.
성공이 영원히 안 보이는 것보다 낫다는 판단이므로 되돌리지 마라.

[하지 말 것]
- serverState 열거형 구조 자체는 건드리지 마라. 그건 12번 단계에서 한다.
- 전체 재작성 금지. 최소 수정만.

[완료 기준]
- 빌드 통과, 기존 테스트 전부 통과
- 1번 로그에서 reconnectAttempt 가 0->1->0 으로 왕복하지 않고 실제로 누적될 것
- pull 이 성공하면 "서버 동기화됨" 이 뜰 것

4번 — 네 번째로 해야 됨
    .syncing 영구 고착의 유일한 미해결 경로

###
WriterPad/Sync/SyncV2SnapshotPull.swift 의 SyncV2WorkspaceSyncModel 에서
pullTask 가 영구히 non-nil 로 남을 수 있는 경로와
pullPending 드레인 주체가 죽는 경로를 막아줘.

[확정된 결함 A — watchdog 밖의 await]
performPullWithAuthenticationRetry 안의
    let state = await authenticationService.refreshSession(force: true)
가 pullTask 본문에서 유일하게 시간 상한이 없는 await 다.
performWatchdogPull 은 15초 상한이 있고, race.value() 는 취소 불가지만
watchdog Task 가 비구조적 Task 라 취소를 상속하지 않아 반드시 발화한다.
즉 pullTask 는 "본문이 종료되기만 하면" 반드시 nil 로 돌아온다.
종료 보장이 없는 곳이 위 한 줄뿐이다.
여기가 막히면 이후 모든 pullNow 가 pullPending = true 로만 병합되고
serverState 가 .syncing 에 영구 고정된다.
이 경로는 토큰 만료(=유휴) 후에만 진입한다.

[확정된 결함 B — 드레인 주체 사망]
finishPull 의 구조가
    guard pullRequestID == requestID else { return }        // (1) 드레인 안 함
    pullTask = nil
    guard generation == requestGeneration, isActive else { return } // (2) 안 함
    ...
    if pullPending { pullPending = false; await pullNow() }  // 드레인은 여기뿐
라서, (2)에 걸리면 pullPending 이 true 로 남고 아무도 소비하지 않는다.
같은 경로에서 serverState 도 .syncing 인 채 방치된다.

[해야 할 것]
1. 결함 A: refreshSession(force: true) 를 watchdog 으로 감싼다.
   파일에 이미 있는 private actor SyncV2WorkspaceAuthenticationOutcome 을
   재사용해 private func refreshWithTimeout() async -> AuthenticationState 를
   추가하고, pullTimeout / pullTimeoutSleep 을 상한으로 쓴다.
   타임아웃 시 .unavailable(.networkUnavailable) 를 반환하고
   refresh Task 는 cancel 한다.
2. 결함 B: finishPull 의 두 번째 guard 를 else 블록으로 바꿔
   pullPending = false 로 비우고, serverState 가 .syncing 이면 .idle 로
   되돌린 뒤 return 한다.
   (scene 재개 경로가 반드시 새 pullNow 를 돌리므로 상태만 비우면 된다.)

[하지 말 것]
- 첫 번째 guard(pullRequestID 대조)의 위치나 의미는 바꾸지 마라.
  현재 로직이 맞다.
- 새로운 race/outcome actor 타입을 추가하지 마라. 기존 타입을 재사용한다.

###
WriterPad/Sync/SyncV2SnapshotPull.swift 의 SyncV2RealtimeConnectGate 가
영구히 잠길 수 있는 구조를 고쳐줘.

[확정된 결함]
    await acquire()
    defer { release() }
    try Task.checkCancellation()
    try await operation()          // <- channel.subscribeWithError()
release() 는 operation() 이 반환해야만 실행된다. 그런데 이 게이트를 도입한
주석이 직접 밝히듯 Supabase SDK 2.46.0 의 subscribeWithError 는 phx_join 에서
영구 대기할 수 있고, 취소를 무시할 수 있다. 그러면 isHeld = true 가 영구
고정되고, acquire() 의 withCheckedContinuation 은 취소 불가라 이후 모든 구독이
영원히 대기한다.

게다가 AppEnvironment.swift 에서 workspace trigger 와 background trigger 가
SupabaseClientProvider 의 동일한 realtimeSubscriptionGate 인스턴스를 공유한다
(SupabaseClientProvider.makeRealtimeTrigger 가 저장 프로퍼티를 넘긴다).
즉 채널 하나의 hang 이 앱 전체 realtime 을 영구 정지시킨다.

[해야 할 것]
1. withSubscription 에 보유 시간 상한(기본 20초)을 넣어, operation() 이
   반환하지 않아도 게이트가 반드시 풀리게 한다. operation 을 별도 Task 로
   띄우고 timeout Task 와 race 시킨 뒤, 어느 쪽이 이기든 release() 한다.
   방치된 join 은 상위 stop() 이 정리한다.
   race 는 파일에 이미 있는 SyncV2RealtimeStartRace 를 재사용해도 된다.
2. 타임아웃으로 풀린 경우 호출측이 구분할 수 있도록
   SyncV2RealtimeTriggerError 에 전용 case(예: subscriptionTimedOut)를 추가해
   throw 한다. globalSubscriptionUnsupported 를 재사용하지 마라 —
   로그 판독이 불가능해진다.
3. AppEnvironment.swift 에서 두 trigger 가 같은 gate 를 공유한다는 사실을
   주석으로 명시한다. 지금은 우연처럼 보인다.

[하지 말 것]
- 게이트를 없애지 마라. 동시 subscribe 직렬화는 실제 SDK 버그 우회이며
  필요하다.
- acquire() 쪽에 타임아웃을 넣는 대안은 쓰지 마라. 그러면 두 채널이 동시에
  subscribe 해버려 게이트의 존재 이유가 사라진다.

[완료 기준]

- waiters.count 가 단조 증가하지 않을 것

###
WriterPad/Sync/SupabaseAuthService.swift 에서 restore 와 refresh 가
단일 activeOperationID 를 공유해 서로의 결과를 무효화하는 문제를 고쳐줘.

[확정된 결함]
beginOperation() 은 하나의 activeOperationID 만 관리하는데
restoreSession() 과 refreshSession(force:) 가 둘 다 이걸 호출한다.

state 가 .authenticated 인 타이밍에 refresh 가 들어오면 진행 중인 restore 의
operationID 를 탈취한다. 그러면 performRestore 의
    guard isCurrent(operationID) else { return state }
가 실패해 "성공한 restore 결과를 버리고 stale state 를 그대로 반환" 한다.
state 가 .restoring 인 채로 남으면 SyncV2WorkspaceSyncModel.activate() 가
.checkingAuthentication 분기로 빠져 "로그인 확인 중" 스피너가 계속된다.

[확인된 비-결함 — 건드리지 마라]
- activeRefresh / activeRestore 캐시는 누수가 없다. 생성자가
  await task.value 직후 항상 정리하고, Task<_, Never>.value 는 취소로
  중단되지 않는다.
- refreshSession -> restoreSession -> refreshSession 상호 재귀는 데드락이
  아니다. 같은 actor 내부 직접 호출이라 그 사이에 서스펜션 창이 없어
  state 가 뒤바뀔 수 없다.
따라서 "실패한 task 가 캐시에 남는다"거나 "재진입 데드락"이라는 가설로
수정하지 마라. 실제 결함은 operationID 네임스페이스 공유로 인한 결과 폐기다.

[해야 할 것]
1. refreshSession(force:) 에서 activeRefresh 확인 직후,
   state.isAuthenticated 가드 뒤에 activeRestore 확인을 추가해 진행 중인
   restore 가 있으면 그 결과를 그대로 반환한다.
   (새 operation 을 시작하지 않는다.)
2. restoreSession() 에도 대칭으로 activeRefresh 확인을 추가한다.
   refreshSession 이 activeRefresh 설정 시 먼저 반환하므로 루프가 생기지 않는다.
3. 두 곳 모두 "왜 이 확인이 필요한지"(beginOperation 이 단일 ID 를 덮어쓴다)를
   주석으로 남긴다.

[선택 — 판단해서 보고만 해줘]
scheduleAutomaticRefresh 의 delay 계산이
    max(0, sessionExpiresAt.timeIntervalSince(now()) - refreshMargin)
이라, 발급 시점에 이미 만료 5분 이내인 토큰이면 delay 가 0 이 되고
accept() 가 다시 scheduleAutomaticRefresh() 를 불러 즉시 재갱신 루프가 된다.
정상 1시간 토큰에서는 발생하지 않지만 기기 시계 오차나 짧은 토큰에서는
성립한다. 최소 하한(예: 30초)을 두는 게 맞는지 판단해서 알려줘.
임의로 적용하지는 마라.

[완료 기준]
- 빌드 통과, 기존 테스트 전부 통과
- 1번 로그에서 "operation superseded" 가 더는 찍히지 않을 것

###
Task ivar sentinel 패턴을 값 타입으로 봉인해 2번에서 고친 결함 클래스가
재발할 수 없게 만들어줘.

[문제]
    guard xTask == nil else { return }      // 단일 실행 보장
    xTask = Task { ... ; self.xTask = nil } // 해제는 본문 안쪽 한 지점
이 패턴이 SyncV2WorkspaceSyncModel 의 8개 필드
(pullTask, reconnectTask, pullRetryTask, realtimeStartTask, debounceTask,

[해야 할 것]
1. @MainActor 값 타입을 하나 만든다. cancel() 이 nil 대입을 강제하는 것이
   핵심이다.

       @MainActor
       struct SingleFlightTask {
           private var task: Task<Void, Never>?
           var isScheduled: Bool { task != nil }
           mutating func cancel() { task?.cancel(); task = nil }
           mutating func schedule(...) { guard task == nil else { return }; ... }
       }

2. SyncV2WorkspaceSyncModel 의 8개 필드를 순차적으로 이 타입으로 교체한다.
   한 번에 하나씩, 각 교체마다 빌드와 테스트를 돌린다.
3. SyncV2BackgroundSyncCoordinator 의 realtimeTask / reconnectTask /
   debounceTask / periodicTask 에도 같은 타입을 적용한다
   (actor 격리라 별도 변형이 필요하면 만들어라).
   특히 performRealtimeReconnect 의 catch { return } 경로가 reconnectTask 를
   비우지 않는 것도 같은 결함 클래스다.

[하지 말 것]
- pullTask 는 finishPull 의 pullRequestID 대조와 얽혀 있으니 마지막에 손대고,
  의미가 바뀌면 교체하지 말고 그대로 둔 채 보고해라.
- 동작 변경 금지. 순수 리팩터링이며 7번 테스트가 전부 통과해야 한다.

- "cancel 했는데 nil 을 안 넣는" 코드를 작성하는 것이 타입 수준에서
  불가능해질 것

취소 불가 동기화 프리미티브 5벌을 정리해서, 어느 쪽이 "취소 불가가 정상"이고
어느 쪽이 "반드시 상한이 필요"한지 코드에서 구분되게 해줘.

[현황 — 전부 withCheckedContinuation 기반이라 모양이 똑같다]
  SyncV2RealtimeConnectGate      (SyncV2SnapshotPull.swift)  <- 게이트: 상한 필수
  SyncV2DocumentMutationGate     (SyncV2SnapshotPull.swift)  <- 게이트: 상한 필수
  SyncV2WorkspacePullRace        (SyncV2SnapshotPull.swift)  <- 레이스: 취소불가 정상
  SyncV2RealtimeStartRace        (SyncV2SnapshotPull.swift)  <- 레이스: 취소불가 정상
  AuthenticationRestoreOutcome   (SupabaseAuthService.swift) <- 레이스: 취소불가 정상

레이스 3종은 watchdog 이 해소하므로 취소 불가가 의도된 설계다.
게이트 2종은 취소 불가가 곧 영구 잠금이다. 그런데 모양이 같아서 리뷰에서
구분이 안 된다.

[해야 할 것]
1. 레이스 3종의 중복 구현을 제네릭 하나로 합친다.
   (resolve 1회 고정 + value() 대기, 동작은 완전히 동일하므로 순수 통합이다.)
   이름에 Race 를 유지해 "취소 불가가 정상"임을 드러내고, 그 이유를 타입
   주석에 남긴다.
2. 게이트 2종에 "보유 시간 상한"을 공통 기능으로 넣는다.
   5번에서 SyncV2RealtimeConnectGate 에 넣은 것을 SyncV2DocumentMutationGate
   에도 적용한다. SyncV2DocumentMutationGate.acquire 도 취소 불가
   continuation 이라, 한 문서 락이 오래 잡히면 뒤에 줄선 pull 이 전부 대기한다.
3. 게이트 타입 주석에 "이 안의 operation 이 반환하지 않으면 프로세스 전역이
   멈춘다"를 명시한다.

[참고 — 확인은 했지만 확정 결함은 아님]
SyncV2DocumentMutationGate 는 withCriticalSection 이 throw 경로에서도
release 하므로 락 자체는 균형이 맞다. 문제는 acquire 대기가 취소 불가라서,
watchdog 에 버려진 orphan task 들이 문서별 FIFO 큐 앞에 쌓일 수 있다는 점이다.
AppEnvironment 에서 workspace 모델과 background coordinator 가 같은
SyncV2SnapshotPullService / syncMutationGate 인스턴스를 공유하므로 이 축적이
실제로 가능하다. 1번 로그의 대기열 길이로 실제 발생 여부를 먼저 확인하고,
발생하지 않으면 상한만 넣고 끝내라.

테스트의 벽시계 대기를 제거해 CI 플레이크 위험을 없애줘.

[현황]
sleep / clock / now 주입 지점이 77곳이나 되는데도, 테스트에 실제 대기가
58곳 남아 있다.
  .milliseconds(10) x 8,  .milliseconds(80) x 5,  .milliseconds(5) x 5,
  .milliseconds(2) x 3,   .milliseconds(350) x 2,  Task.sleep(nanoseconds:) x 5 ...
대부분 "actor task 가 인터리브할 틈을 준다"는 용도로 보이는데,
부하 걸린 CI 머신에서는 2ms 가 부족하다. 주입 인프라는 이미 다 만들어져 있으니
마무리만 하면 된다.

[해야 할 것]
1. 상태 폴링 헬퍼를 만든다.
       func waitUntil(_ condition: @MainActor () -> Bool,
                      timeout: Duration = .seconds(2),
                      file: StaticString = #filePath,
                      line: UInt = #line) async throws
   내부는 Task.yield() 반복 + 실패 시 명확한 메시지로 XCTFail.
2. "틈을 주는" 용도의 짧은 sleep(2~100ms)을 waitUntil 또는 Task.yield()
   반복으로 교체한다.
3. 남겨야 하는 sleep 은 남기되, 왜 실제 시간이 필요한지 주석을 단다.
   LocalPerformanceBaselineTests 의 16ms 처럼 성능 측정이 목적이면 정당하다.
4. 교체 후 테스트 스위트를 최소 20회 반복 실행해 플레이크가 없는지 확인한다.

[하지 말 것]
- 테스트의 검증 내용을 약화시키지 마라. 대기 방식만 바꾼다.
- 타임아웃을 늘려서 통과시키는 방식 금지. 그건 플레이크를 숨기는 것이다.

[완료 기준]
- 테스트 내 Task.sleep / ContinuousClock().sleep 사용처가 정당한 것만 남을 것
- 20회 연속 전체 통과

###
AppEnvironment 의 조립 책임을 기능별로 분해해줘.

[현황]
AppEnvironment.swift 가 전 계층을 혼자 조립한다.
AppEnvironmentTests.swift 가 4,520줄로 테스트 파일 중 가장 큰데,
이 조립 경로 분기를 전부 검증하기 때문으로 보인다.

[해야 할 것]
1. 기능별 팩토리로 쪼갠다.
   - SyncComposition          auth service, binding service, snapshot pull
                              service, realtime trigger, background coordinator,
                              dispatcher
   - LocalStorageComposition  SwiftData 스택, repository 들, document store
   - BackupComposition        backup store, trash
2. AppEnvironment 는 이 팩토리들을 호출해 조립만 담당하게 한다.
3. AppEnvironmentTests 에서 각 팩토리 단위로 테스트 가능한 부분을 분리한다.
   테스트 총량을 억지로 줄이지는 마라. 표면을 나누는 것이 목적이다.
4. 조립 중 발견되는 "공유 인스턴스"에 의도를 주석으로 명시한다.
   특히 snapshotPullService 와 syncMutationGate 를 workspace 모델과
   background coordinator 가 공유하는 부분(문서 단위 락이라 정합성은 맞지만
   한쪽의 지연이 다른 쪽 대기열에 쌓인다)은 반드시 명시한다.
   9번에서 이미 주석을 달았다면 중복하지 말고 참조만 남겨라.

[하지 말 것]
- 의존성 주입 구조 자체를 바꾸지 마라. 프로토콜 50개 기반 구조는 잘 되어 있다.
- 동작 변경 금지.

[완료 기준]
- 빌드 통과, 기존 테스트 및 7번 테스트 전부 통과
- AppEnvironment.swift 가 "무엇을 조립하는지"만 읽어도 파악될 것
