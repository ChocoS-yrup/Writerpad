# 편집용 로컬 사본 — 수동 TXT 내보내기 계약

2026-09-21. 검증된 `ReceiveEditable-v1` 작업 사본을 사용자가 선택한 외부 파일 위치에 저장하는 첫 범위를 정한다. 계약 수립 시점에는 코드, 기기, 설치물, 인증, 서버를 변경하지 않았고, 아래 후속 절에 구현과 검증 결과를 이어서 기록한다.

## 결정

첫 버전은 **현재 선택한 저장 완료 문서 한 개를 UTF-8 TXT로 수동 내보내기**만 제공한다.

- 앱이 자동으로 내보내거나 공유하지 않는다.
- 미저장 초안이 있는 문서는 내보낼 수 없다.
- 내보내기 버튼을 누른 뒤 대상 이름·local revision·byte 수·SHA-256을 검토하고 사용자가 계속을 선택해야 한다.
- iOS 파일 내보내기 화면에서 사용자가 위치와 최종 파일명을 직접 선택한다.
- 서버 업로드, 공유 시트, 메일·메신저 전송, WriterPad 가져오기, 송신 큐 생성은 포함하지 않는다.

## TXT 바이트 계약

내보낸 파일은 저장 완료 `workspace.json` 문서 본문의 UTF-8 바이트와 정확히 같아야 한다.

- UTF-8 BOM을 추가하지 않는다.
- 줄바꿈을 추가·제거·변환하지 않는다.
- 빈 문서는 0바이트 TXT로 허용한다.
- 제목, 작품명, revision, hash, 생성 시각을 본문 앞뒤에 삽입하지 않는다.
- NFC/NFD 정규화, 공백 정리, 금칙어 치환을 하지 않는다.
- 문서당 기존 4 MiB 상한을 그대로 사용한다.

파일명 기본값은 검증된 문서 이름을 그대로 사용한다. 문서 이름은 기존 `validateComponent`를 통과한 값이어야 하며 `/`, `..`, 절대경로, 제어 문자, 숨은 경로 승격을 허용하지 않는다. `.txt`가 이미 있으면 다시 붙이지 않는다. 첫 버전은 전체 폴더·ZIP·PDF·복구 패키지를 만들지 않는다.

## 외부에 포함하지 않는 정보

TXT에는 다음을 넣지 않는다.

- local ID, source run, 원격 project/document UUID
- 원본·작업 사본 경로
- identity/workspace/save journal JSON
- 설정 파일, endpoint, account ID, publishable key
- 인증 정보, 세션, 승인, 실행 기록

출처 폴더명, 문서명, local revision, byte 수와 SHA-256은 내보내기 전 앱 화면에서만 표시한다. 첫 버전은 sidecar manifest를 만들지 않는다. 따라서 TXT만으로 앱 내부 provenance를 복구한다고 주장하지 않는다.

## 준비와 실행 경계

1. 현재 저장된 수신 원본과 작업 사본을 다시 검증한다.
2. 선택 문서의 저장 완료 본문, ID, 이름, local revision, byte 수, SHA-256과 workspace 파일 SHA-256을 불변 내보내기 후보로 메모리에 고정한다.
3. 화면의 현재 초안이 저장 완료 본문과 다르면 내보내기 버튼을 비활성화하고 `먼저 로컬 저장을 완료하세요`를 표시한다.
4. 사용자에게 문서명, revision, byte 수, SHA-256과 `본문 TXT만 내보냅니다`를 보여 준다.
5. 사용자가 계속을 선택하면 SwiftUI `fileExporter`의 메모리 `FileDocument`로 시스템 파일 위치 선택 화면을 연다. 앱 소유 임시 파일을 만들지 않는다.
6. 파일 위치 선택 중 앱이 비활성화되어 기존 lifecycle lease가 폐기될 수 있으므로, 내보내기 payload는 선택 화면을 열기 전에 완성된 불변 메모리 값이어야 한다.
7. 시스템이 반환한 URL을 security-scoped 범위에서 한 번 다시 읽어 크기와 SHA-256을 후보와 대조한다.
8. 앱이 다시 active가 된 뒤 새 lease로 원본과 작업 사본을 재검증하고 준비 당시 workspace SHA-256과 일치하는지 확인한다.
9. 외부 파일 재읽기와 내부 재검증이 모두 통과한 경우에만 `내보내기 완료 · 원본과 작업 사본 변경 없음`을 표시한다.

파일 공급자가 저장은 받았지만 즉시 재읽기를 허용하지 않으면 성공으로 표시하지 않는다. `파일 저장 결과를 재검증하지 못했습니다`로 표시하며, 원본이나 작업 사본을 변경·삭제하지 않는다. 외부 파일이 이미 존재할 가능성을 사용자에게 알리고 자동 재시도하지 않는다.

## 위치와 이름 충돌

- 앱은 기존 외부 파일을 미리 삭제하거나 덮어쓰지 않는다.
- 같은 이름이 있으면 iOS 파일 선택 화면의 취소·대치·새 이름 선택 결과를 따른다.
- 사용자가 대치를 명시적으로 선택한 경우에도 앱은 반환된 최종 파일을 다시 읽어 hash를 확인한다.
- 시스템이 반환한 최종 URL의 이름이 기본값과 달라도 본문 hash가 같으면 허용하고, 최종 이름을 결과 화면에 표시한다.
- 앱 내부 원본·작업 사본 파일명이나 identity는 외부에서 선택한 이름으로 바꾸지 않는다.

## 로컬 저장 위치와 동기화 안내

앱 자체는 네트워크 요청을 하지 않지만, 사용자가 파일 앱에서 iCloud Drive나 제3자 파일 공급자를 고르면 해당 공급자가 파일을 동기화할 수 있다. 오프라인 보관이 목적이면 내보내기 검토 화면에서 **나의 iPad** 같은 로컬 위치를 선택하도록 안내한다.

첫 버전은 특정 파일 공급자를 기술적으로 허용·차단한다고 주장하지 않는다. 네트워크 0이 필요한 검증에서는 비행기 모드로 실행하고 로컬 위치를 선택한다.

## 취소·실패·lifecycle

- 검토 취소와 파일 선택 취소는 성공 기록을 만들지 않는다.
- 앱 비활성화·잠금·보호 데이터 사용 불가 시 내보내기 결과 검증을 중단한다.
- 다시 active가 됐다고 이전 lease나 준비 payload를 자동 재사용하지 않는다. 반환 결과를 처리할 때 내부 사본을 새로 검증한다.
- 외부 쓰기, 재읽기, hash 대조, 내부 재검증 중 하나라도 실패하면 원본·작업 사본을 그대로 두고 실패 원인을 구분해 표시한다.
- 외부 파일 실패를 이유로 `workspace.json`, save journal, revision을 되돌리거나 새로 저장하지 않는다.
- 내보내기 중 로그인·인증·수신·송신·자동 재시도를 시작하지 않는다.

## 화면 문구와 버튼

편집 화면에서 현재 문서 아래에 다음을 둔다.

- 버튼: `저장된 본문 TXT 내보내기`
- dirty 상태: `먼저 로컬 저장을 완료하세요`
- 검토 제목: `저장된 본문 내보내기`
- 검토 설명: `본문 TXT 한 개만 내보냅니다. 원본·작업 사본·서버 상태는 변경하지 않습니다.`
- 성공: `내보내기 완료 · 원본과 작업 사본 변경 없음`
- 사용자 취소: `내보내기를 취소했습니다`
- 외부 재읽기 실패: `파일 저장 결과를 재검증하지 못했습니다`
- 내부 사본 변화: `내보내기 확인 차단 · 작업 사본이 변경됐습니다`

내보내기 버튼을 로그인·승인·실행 버튼과 같은 화면에 추가하지 않는다. 공유 아이콘만 두어 자동 공유로 오해하게 하지 않는다.

## 구현 전 검사 목록

1. 한글·빈 문서·마지막 LF가 내보내기 전후 byte-identical
2. 미저장 초안이 있으면 준비·파일 선택 모두 시작되지 않음
3. 검토 취소와 파일 선택 취소에서 외부 성공 표시·내부 변경 없음
4. 이름 충돌에서 앱이 기존 파일을 선삭제하지 않음
5. 외부 쓰기 실패·부분 파일·재읽기 거부·hash 불일치에서 fail closed
6. 파일 선택 중 scene 비활성화와 복귀 뒤 새 lease로 내부 재검증
7. 준비 뒤 workspace가 바뀌면 성공 표시 차단
8. 원본·작업 사본 전체 파일이 내보내기 전후 byte-identical
9. HTTP·인증·승인·송신 큐 호출 0
10. TXT에 identity, 설정, journal, 계정·세션 정보가 없음

## 제외 범위

- 전체 작품·여러 문서 일괄 내보내기

- Files 앱에서 가져오기 또는 WriterPad로 승격

- iCloud·제3자 공급자 동기화 성공 보장
- 외부 파일 삭제·버전 관리·재가져오기

## 판정

수동 TXT 내보내기는 저장 완료 문서 한 개의 정확한 UTF-8 바이트를 사용자가 선택한 위치로 복사하는 소장 기능이다. 백업·복원·동기화·WriterPad 승격 기능으로 취급하지 않는다. 이 계약을 기준으로 순수 payload 생성·결과 검증기와 격리 검사를 먼저 구현한다.

## 순수 payload 구현 결과

2026-09-21에 UI와 외부 쓰기를 제외한 첫 구현을 완료했다.

- `ReceiveEditableExport.prepare`는 저장 완료 본문과 화면 초안이 같은 경우에만 불변 UTF-8 payload를 만든다.
- 기본 파일명은 검증된 문서명을 사용하며 `.txt`가 없을 때만 붙인다.
- payload는 본문 byte 수와 SHA-256, 문서 ID·revision, 준비 당시 전체 작업 사본의 정렬된 결합 SHA-256을 메모리에 보관한다.
- 외부 결과는 byte 수·SHA-256·전체 바이트가 모두 같아야 통과한다.
- 복귀 후에는 source run, 폴더명, 모든 문서의 ID·이름·revision·본문 hash를 다시 결합해 준비 당시 값과 대조한다.
- 이 내부 결합 정보는 TXT 본문에 포함하지 않는다.
- 화면, `fileExporter`, 외부 URL 접근, 기기 설치·실행은 이번 구현에 포함하지 않았다.

검증 결과:

- 내보내기 전용 검사 7개 통과
- 기존 편집 사본 검사 9개 포함 총 16개 통과
- 일반 iOS 기기 대상 서명 없는 Debug 빌드 성공

## 화면·시스템 파일 내보내기 연결 결과

2026-09-21에 편집 화면의 명시적 검토와 SwiftUI `fileExporter` 연결을 완료했다.

- 저장 완료 문서에만 `저장된 본문 TXT 내보내기` 버튼이 활성화된다.
- 검토 화면은 파일명, local revision, byte 수, SHA-256과 로컬 위치 안내를 표시한다.
- 사용자가 `파일 위치 선택`을 누른 뒤에만 시스템 파일 화면을 연다.
- `FileDocument`는 메모리에 고정한 본문 바이트만 쓰며 앱 소유 임시 파일을 만들지 않는다.
- 시스템이 성공 URL을 반환하면 예상 크기보다 한 바이트까지만 제한해서 다시 읽고 payload와 대조한다.
- 파일 화면으로 인한 lifecycle 폐기 뒤에는 보관 원본을 다시 읽고 작업 사본을 디스크에서 다시 열어 전체 결합 SHA-256을 대조한다.
- 외부 파일과 내부 자료 검증이 모두 통과한 경우에만 완료 문구를 표시한다.
- 취소, 외부 재읽기 실패, 작업 사본 변경을 서로 다른 문구로 표시한다.

로컬 검증 결과:

- 기존 편집 사본 및 내보내기 검사 16개 통과
- iOS 일반 기기 대상 서명 없는 Debug 빌드 성공
- 기기 설치·실행, 인증, 서버 요청 없음

## 실제 기기 1회 검증 결과

2026-09-21 실제 iPad에서 비행기 모드와 무선 통신 차단 상태로 `저장경계.txt`를 `나의 iPad`에 수동 내보냈다.

- 설정 SHA-256: `de21e047a0ba7786920ba901a4a6e228d6cb5faab0654c05e13b988b798ca24e`
- 실행 파일 SHA-256: `62c32ebdd1f112b777456e32a3f1f0400658e29d76cc5086b99503504af27a2b`
- 앱에서 `내보내기 완료 · 원본과 작업 사본 변경 없음`을 확인했다.
- 파일 앱의 `나의 iPad`에서 최종 TXT 파일 존재를 확인했다.
- 설치 전후 백업과 설정 전달 기록을 별도 보존했다.

내보내기 전후 앱 소유 저장 영역을 다시 계산한 결과:

- `ReceiveConfiguration-v1`: 3개 파일 전체 SHA-256 동일
- `ReceiveDedicated-v1`: 21개 파일 전체 SHA-256 동일
- `ReceiveEditable-v1`: 3개 파일 전체 SHA-256 동일
- `WriterPadReceiveBoundary-v1`: 17개 파일 전체 SHA-256 동일

전체 컨테이너 비교에서 달라진 항목은 `Library/Caches/com.apple.dyld`와 `Library/Saved Application State`뿐이었다. 이는 앱 실행·종료에 따라 iOS가 관리하는 실행 캐시와 창 복원 상태이며, 수신 원본·설정·전용 실행 자료·편집 사본에는 차이가 없었다. 인증과 서버 요청은 수행하지 않았다.

## 파일 선택 lifecycle 보완

최종 파일명 표시를 추가한 후보를 설치해 다시 확인하는 과정에서 시스템 파일 화면이 scene을 비활성화하면 편집 sheet의 로컬 `pendingExport`도 함께 폐기되는 문제가 확인됐다. 외부 파일이 만들어져도 앱 복귀 후 재검증이 이어지지 않았으며, 읽기 전용 화면에는 `앱 상태가 변경되어 자료 표시를 닫았습니다`가 표시됐다. 이 시도는 성공으로 판정하지 않는다.

수정 결과:

- 대기 중인 불변 payload와 시스템 반환 URL을 `IOSBoundaryController`가 메모리에서 보관한다.
- scene 비활성화 때 기존 snapshot과 lease는 계속 폐기한다.
- scene이 다시 active가 되면 컨트롤러가 새 lease로 외부 결과와 내부 원본·작업 사본을 재검증한다.
