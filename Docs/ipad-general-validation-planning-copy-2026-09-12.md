# iPad 예상 상태 산출용 격리 복제

## 범위

`GeneralValidationPlanningCopy`는 로컬 SQLite 두 개와 작품 파일을 새 private 디렉터리에 복제하고, 복제본에서 단계별 예상 체크포인트를 산출하는 내부 구성이다. 원본과 복제본의 논리 해시를 대조하며 SQLite 복제에는 backup API를 사용해 커밋된 WAL 내용을 포함한다. 원본에서 migration·WAL checkpoint·파일 저장을 실행하지 않는다. 앱 화면이나 실기기에는 연결하지 않았다.

파일은 복제 경로에서 읽되 해시의 작품 경로 기준은 원본 경로로 고정한다. 그러므로 임시 디렉터리 이름 차이가 상태 차이로 계산되지 않는다. 심볼릭 링크와 작품 폴더 안의 복제 목적지를 거부하고, 기존 복제 디렉터리를 재사용하거나 삭제하지 않는다.

WAL DB를 backup한 직후 복제본의 첫 읽기 전용 열기가 실패하는 현상을 검사에서 발견했다. 복제 대상 연결에서만 `journal_mode=DELETE`를 적용해 독립적으로 읽을 수 있도록 했다. 원본 연결에는 해당 PRAGMA를 실행하지 않는다.

제품 저장소를 다시 열 때 전역 시작 복구가 다른 작품의 batch 수정 시각까지 갱신하는 현상도 발견했다. `GeneralValidationMutation` 문맥에서는 이 시작 복구를 생략한다. 일반 실행의 시작 복구는 기존 조건을 유지한다. 마이그레이션이나 복구를 가정하고 예상 계획을 실제 실행에 바로 적용하는 것은 허용하지 않는다.

`derive`는 복제 경로를 사용하는 로컬 반영 콜백을 호출하고 매 단계 원본 상태가 유지되는지 확인한다. 기존 제품 HTTP 경계에서 로컬 변경 문맥의 세션을 차단하며, 새로운 송수신 권한을 부여하지 않는다. 임의 콜백을 파일 시스템 수준에서 격리하는 보안 장치는 아니므로 실제 앱 구성에는 반드시 복제 전용 repository·store·workspace를 전달해야 한다.

## 실제 실행 연결 전에 남은 일

복제본에서 계산한 해시를 실제 저장소 실행의 예상값으로 사용하려면 비결정적 입력을 실행 전에 고정해야 한다. 다음 지점이 확인됐다.

- `GeneralValidationProductAdapter.saveAndCaptureRequest`: 현재 시간에서 저장 generation을 만든다.
- `LocalDocumentStore`: durable batch/operation UUID를 생성하고, 저장한 임시 파일의 실제 수정 시각을 메타데이터에 기록한다. clock 주입만으로 파일 수정 시각까지 고정되지는 않는다.
- `SyncV2Store`: 계약 큐·완료·수신 기준 반영에 내부 timestamp를 기록한다.
- SwiftData: 복제 저장소를 열고 새 행을 반영한 결과까지 포함해 원본 실행과 재현되는지 확인해야 한다.

이 입력을 고정한 제품 경로의 독립 재실행 대조가 끝나기 전에는 예상 계획을 실기기 송수신에 사용하지 않는다. 이번 작업은 계획 산출 기반이며 전체 실행 준비 완료를 의미하지 않는다. Windows 공통 계약은 변경하지 않았다.

## 검증 결과

- 격리 검사 91개와 일반 시작 복구·수신 잠금 회귀 4개, 합계 95개 통과.
- 커밋된 WAL 내용 포함, 원본 main DB·WAL 바이트 유지, 원본 변경 시 산출 중단, 심볼릭 링크·작품 내부 목적지 거부를 확인.
- 실제 제품 SQLite·디스크 SwiftData·기존 수신 코드로 복제본의 `receiveWindows → sendUpdate` 예상 상태를 산출. 원본 본문은 생성되지 않았고 다른 작품의 큐 행도 보존됨.
- 저장·완료 2단계 계획 산출은 합성 SQL·파일 변경으로 검증했으며 실제 저장·송신의 결정적 재현을 검증한 것은 아님.
- 고정 소스 234개가 작업 폴더와 일치. 서명 없는 ARM64 빌드 성공, 검증 보호 코드 포함 및 격리 테스트 코드 제외 확인.
- 실기기 설치·실서버 접속·프로파일 갱신 0회. 만료된 프로파일로 후보 서명을 재시도하지 않음.
