# Cached session and native HTTP boundary

`SupabaseCachedSessionBridge.swift` is typechecked against the retained Supabase Swift 2.46.0 modules. It is not added to the demonstration app's dependencies or instantiated with a real client. The factory is passive; the callback reads `client.auth.currentSession` only when invoked. It does not use the refreshing async `session` API or subscribe to initial auth events, which can refresh an expired session in this SDK.

The owner must supply a thread-safe cached-session reader and mutation epoch. All auth mutations, including logout/login with the same token, must advance that epoch. Callbacks may run on the URLSession delegate/deadline queues. This work does not install that hook in the existing Auth owner, create a client, read the keychain, or change the owner's refresh policy. Captured credentials are non-Codable and have redacted descriptions/mirrors; this does not promise secure erasure of Swift strings or system memory.

The shared `ReceiveSessionBoundary.swift` and `ReceiveHTTPConnection.swift` compile in the isolated iOS target. The native connection fixes the account/project and the two Q1–Q7 request passes. It accepts a publishable key only; legacy anon JWT compatibility is not assumed. A closed live connection rejects work before accessing a session or constructing URLSession. Only the explicit `.invalid` test origin is enabled with a test URLProtocol and mandatory catch-all deny protocol. This is application-level interception, not an OS network sandbox or production grant.

An admitted request requires a caller-owned durable reservation/start callback before the first suspension and task resume. Callback I/O, cached-session checks and request setup consume the request deadline. The operation uses ephemeral URLSession without cache/cookies/stored credentials; it bounds raw response bytes, rejects redirects and credential challenges, and cancels on expiry, session/lifecycle changes, task cancellation or deadline. Server trust uses the OS default. Real TLS, server-side request count, OS connection recovery and remote cancellation are unverified.

The 200/206 response remains raw and unverified. Content-Range is preserved, not interpreted as completeness. Auth identity, handshake, row/count/order/body semantics and A/B consistency require the existing receive contract validators. No baseline is applied by this component.

The durable callback was tested with a new temporary on-disk journal, including charge preservation and restart rejection after a stubbed 401.

The next offline integration adds `ReceiveAuthOwner` with begin/finish mutation tickets. Begin revokes the previous cached session before any asynchronous action; stale, duplicate or foreign completion tickets cannot publish. `withReceiveSupabaseAuthChange` maps an explicitly supplied SDK operation result into that owner. It does not create an Auth operation, attach to the existing application's client, or subscribe to events. Production owners must route every relevant mutation through the hook; an unreported external SDK mutation is not detectable from this independent owner cache. No refresh token is copied.

`ReceiveABCoordinator` now couples the owner lease, native URLSession protocol double, existing A/B validators and protected disk journal for the fixed synthetic fixture. Its async entry uses one dedicated thread for the whole journal run. The old pthread-affine disk implementation and flock are retained; that thread waits for each native async response and checks cancellation, session, lifecycle and budgets during the wait. All reserve/start/metadata/raw/finish writes remain on the journal thread. The native send callback consumes an already read-back reservation; it does not debit again or read the journal on a URLSession thread. The caller is resumed only after journal locks are released. Completion reads recheck the session, protection lease and persisted digest.

The synchronous runner accepts an internal transport protocol so its validation, charging and stop rules are reused. The integration still accepts only the fixed synthetic target and `.invalid` URLProtocol path, writes synthetic journal context, and exposes no baseline/app execution authority. A real account/session context, actual application Auth hook activation, authorization and device verification remain outside this offline integration. Synchronous file I/O cannot be preempted; the dedicated worker waits for its return and rejects late success. Native cancellation does not prove a server stopped processing. No source here is an instruction to run a real request.
